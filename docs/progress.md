**App — `src/lib/live.js` (`useLiveReload`)**

- subscribe `postgres_changes` (`event: '*'`) ทั้ง 4 ตารางใน channel เดียว แล้วเรียก `reload` ของหน้านั้น
  **event เป็นแค่สัญญาณว่า "มีของใหม่"** — ไม่อ่านค่าจาก payload และไม่คำนวณเงินเอง
  ค่าทุกตัวยังมาจาก `receivable_summary` / `payments` / `audit_logs` (architecture.md ข้อ 7)
- **รวบ event ที่มาติดกันเป็นการโหลดครั้งเดียว** (หน่วง 400 ms): การบันทึก 1 ครั้งทำให้เกิด 2 event ขึ้นไปเสมอ
  (แถวในตารางหลัก + แถวใน `audit_logs` ที่ trigger เขียน) และบางงานแตะ 3 ตาราง (สร้างบริษัทใหม่ + การ์ด)
- **โหลดใหม่เสมอเมื่อกลับมาที่แท็บ / แอป หรือเน็ตกลับมา** เพราะมือถือมักตัด websocket ตอนพักแอป
  แล้ว event ช่วงนั้นหายไปเงียบ ๆ — เชื่อ Realtime อย่างเดียวไม่ได้:

  | สัญญาณ | เมื่อไหร่ |
  |---|---|
  | `visibilitychange` (เป็น visible) | สลับแท็บกลับมา / ปลดล็อกจอ |
  | `focus` | คลิกกลับเข้าหน้าต่าง |
  | `pageshow` (เฉพาะ `persisted = true`) | กดย้อนกลับแล้วหน้าถูกคืนจาก bfcache (iOS Safari) |
  | `online` | เน็ตกลับมา |
  | `SUBSCRIBED` รอบที่ 2 ขึ้นไป | channel ต่อใหม่สำเร็จหลังหลุด (ช่วงที่หลุดอาจมี event ที่ไม่ได้รับ) |

### RLS กับ Realtime — ทำไมยังปลอดภัย

- Realtime ตรวจ policy `SELECT` ของผู้ใช้ **เป็นรายแถว** ก่อนส่ง event จึงส่งเฉพาะแถวที่ผู้ใช้มีสิทธิ์อ่าน
- `anon` ถูก `revoke all` ทั้ง 4 ตารางใน 002 → ผู้ที่ไม่ล็อกอิน **ไม่ได้รับ event เลย**
- ผู้ใช้ที่ `is_active = false` มี `my_role()` เป็น null → policy ไม่ผ่าน → ไม่ได้รับ event
- supabase-js ส่ง JWT ของผู้ใช้ให้ Realtime เอง (`INITIAL_SESSION` / `SIGNED_IN` / `TOKEN_REFRESHED`)
  ไม่ต้องเรียก `setAuth()` ในโค้ดของเรา
- **ไม่มี DELETE ในระบบนี้** (ใช้ `is_cancelled` / `is_active`) จึงไม่ติดข้อจำกัดที่ event ของ DELETE ไม่ผ่าน RLS
- Realtime ไม่ได้ให้สิทธิ์เพิ่มกับใคร: การเขียนยังผ่าน RLS + trigger เหมือนเดิมทุกอย่าง

#### วิธีทดสอบ (ทำทั้ง 2 บัญชี: owner และ sales)

1. ล็อกอินเป็น **sales** → กดชื่อตัวเองมุมขวาบน → ต้องเห็นปุ่ม **"เปลี่ยนรหัสผ่าน"** เหนือ "ออกจากระบบ"
2. กดปุ่ม → เมนูปิด กล่อง "เปลี่ยนรหัสผ่าน" เปิด (บนคอมโฟกัสช่องแรกให้เอง บนมือถือไม่โฟกัส)
3. **กดบันทึกโดยไม่กรอกอะไร** → "กรอกให้ครบทุกช่อง"
4. กรอก `1234567` ทั้ง 2 ช่อง (7 ตัว) → "รหัสผ่านใหม่ต้องมีอย่างน้อย 8 ตัวอักษร"
5. กรอกช่องแรก `newpass1234` ช่องที่สอง `newpass9999` → "รหัสผ่านใหม่ทั้งสองช่องไม่ตรงกัน"
6. กรอกให้ตรงกันและยาว ≥ 8 → กด **บันทึก** → กล่องปิด + toast "เปลี่ยนรหัสผ่านแล้ว…"
   **และยังอยู่ในแอป ไม่ถูกเตะออก** (ข้อมูลในหน้าตารางยังอยู่ครบ)
7. กด "ออกจากระบบ" → ล็อกอินด้วย **รหัสเก่า** → ต้องขึ้น "อีเมลหรือรหัสผ่านไม่ถูกต้อง"
8. ล็อกอินด้วย **รหัสใหม่** → เข้าได้
9. **สลับภาษาเป็น EN** แล้วเปิดกล่องอีกครั้ง → ป้ายและข้อความ error ทุกอันต้องเป็นอังกฤษ
10. ทำข้อ 1–8 ซ้ำด้วยบัญชี **owner** → ต้องใช้ได้เหมือนกัน (owner เปลี่ยนรหัสของตัวเองได้)
11. **มือถือ (iPhone Safari / Android Chrome)** ผ่าน Vercel: เปิดกล่อง → ช่องรหัสไม่ทำให้จอซูมเข้า
    (font-size 16px) · คีย์บอร์ดไม่ทับปุ่มบันทึก · กดพื้นหลังนอกกล่องแล้วกล่องปิด
12. **ไม่มีสัญญาณ:** เปิดโหมดเครื่องบิน → กดบันทึก → "เชื่อมต่ออินเทอร์เน็ตไม่ได้…"
13. **ปุ่มย้อนกลับของเครื่อง / Esc** ขณะกล่องเปิด → กล่องปิด ไม่ออกจากหน้า
14. **ไม่มี error ใน console** ทั้งคอมและมือถือ
15. ตารางสิทธิ์ (prd.md ข้อ 9): แถวนี้เป็น ✓ / ✓ จึง **ไม่มี role ผิดให้ทดสอบ** —
    แต่ยืนยันว่าหลังเปลี่ยนรหัส owner **ยังไม่มีปุ่มเพิ่ม/แก้ไข** และ role ยังเป็น "เจ้าของบริษัท"
    (`updateUser` ไม่แตะ `profiles`)
