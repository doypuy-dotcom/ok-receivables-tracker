## M0 — Scaffold + deploy ✓ (4 ต.ค.)
- Vite + React, supabase-js, หน้าเช็คการเชื่อมต่อ, deploy บน Vercel
- **ทดสอบ:** เปิด URL บนมือถือผ่าน 5G แล้วสถานะเป็นสีเขียว ✓

## M1 — Login + role (5 ต.ค.)
- Migration: enum `user_role`, ตาราง `profiles` + RLS, function `my_role()`
- หน้า login (อีเมล + รหัสผ่าน), ออกจากระบบ, จำ session
- อ่าน role จาก `profiles` แสดงชื่อ + ตำแหน่งที่มุมขวาบน, ป้องกันหน้าที่ต้องล็อกอิน
- ปิด sign-up ใน Supabase, สร้างบัญชีทดสอบ 2 บัญชี (owner / sales)
- **ทดสอบ:**
  - ล็อกอินทั้ง 2 บัญชีในคนละเบราว์เซอร์ เห็นตำแหน่งถูก
  - รหัสผิด → ข้อความชัดเจน
  - บัญชีที่ `is_active = false` → เข้าไม่ได้
  - ปิดแท็บแล้วเปิดใหม่ → ยังล็อกอินอยู่

## M2 — ตาราง + RLS + trigger (5 ต.ค.)
- Migration: enums ที่เหลือ, `companies`, `receivables`, `payments`, `audit_logs` ตาม schema.md
- RLS policy ทุกตารางตามตารางสิทธิ์ใน schema.md ข้อ 5
- Trigger: เขียน `audit_logs` (พร้อม `receivable_id`), กันยอดจ่ายเกินยอดรวม, กันจ่ายในการ์ดที่ยกเลิก, ใส่ `updated_at/updated_by`
- View `receivable_summary` ตาม schema.md ข้อ 4
- `supabase/tests/m2_checks.sql`: ชุดคำสั่งตรวจ PASS/FAIL
- **ทดสอบ (PASS/FAIL):**
  1. owner insert ลง `payments` → ถูกปฏิเสธ
  2. sales DELETE แถวใดก็ได้ → ถูกปฏิเสธ
  3. ยอดรวม 10,000 จ่าย 6,000 แล้วจ่ายอีก 5,000 → ถูกปฏิเสธ
  4. ยอดรวม 2,000 จ่าย 500 → `balance` = 1,500
  5. สร้างการ์ดซ้ำ บริษัทเดิม เดือนเดิม → ถูกปฏิเสธ; ยกเลิกการ์ดแรกแล้วสร้างใหม่ → ผ่าน
  6. แก้ยอดการจ่าย → มีแถว `audit_logs` ที่มี `old_value`, `new_value`, `receivable_id` ถูกต้อง
  7. แก้หรือลบ `audit_logs` → ถูกปฏิเสธ
  8. `actual_due_date` เมื่อวาน, จ่ายยังไม่ครบ → `days_to_actual_due` = −1 (ตามเวลาไทย)

## M3 — หน้าจอหลัก (6 ต.ค.)
- หน้าตารางยอดค้าง ตาม ui-reference: ตัวกรองเดือน (หลายเดือน / ทั้งหมด / เฉพาะค้าง), "ข้อมูล ณ", ยอดรวม 2 กล่อง
- การ์ดค้างข้ามเดือนปักบนสุดพร้อมหมายเหตุ, การ์ดปกติ, การ์ดจ่ายแล้ว + สรุปผล
- หน้ารายละเอียดการ์ด: บัญชี, แถบ 3 แถบ, รายการเงินเข้า (กรองเดือนได้), ประวัติการแก้ไข
- ไทย / อังกฤษ
- **ทดสอบ:** ใส่ข้อมูลตัวอย่างผ่าน SQL (บริษัท `[TEST]`) ครบทุกสถานะ แล้วตรวจว่าแสดงตรงกับ ui-reference ทั้งบนคอมและมือถือ

## M4 — ฟอร์มกรอกข้อมูล (6 ต.ค.)
- (sales) เพิ่ม/แก้ไขยอดค้าง: เลือกหรือพิมพ์บริษัทใหม่, แสดงวันครบกำหนดเครดิตทันที, ยกเลิกแบบยืนยัน 2 ขั้น
- (sales) เพิ่ม/แก้ไข/ยกเลิกการจ่าย: โอน/เช็ค, ป้ายวันที่เปลี่ยนตามวิธีจ่าย
- (sales) รายชื่อบริษัท: ดู, เพิ่ม
- ข้อความ error จาก database แปลเป็นภาษาคน (เช่น "ยอดเกินยอดคงเหลือ", "การ์ดของบริษัทนี้ในเดือนนี้มีอยู่แล้ว")
- **ทดสอบ:** owner ไม่เห็นปุ่มแก้ไข และเรียก API ตรงจาก console ก็ถูก RLS ปฏิเสธ; ทุกการแก้ไขโผล่ในประวัติการแก้ไข

## M5 — Realtime ✓ (6 ต.ค.)
- Migration `004_realtime.sql`: เปิด Realtime ให้ `companies`, `receivables`, `payments`, `audit_logs`
- หน้าตารางและหน้ารายละเอียด subscribe แล้ว**โหลดใหม่จาก view / ตาราง** (ไม่คำนวณเองจาก event),
  รวบ event ที่มาติดกันเป็นการโหลดครั้งเดียว, อัปเดต "ข้อมูล ณ"
- โหลดใหม่เสมอเมื่อกลับมาที่แท็บ/แอป หรือเน็ตกลับมา (มือถือตัดการเชื่อมต่อตอนพักแอป)
- การ์ดที่เปิดดูอยู่ถูกยกเลิกโดยคนอื่น → แจ้งข้อความแล้วพากลับหน้าตาราง
- RLS ยังบังคับอยู่: Realtime ส่งเฉพาะแถวที่ผู้ใช้มีสิทธิ์อ่าน
- เลขเวอร์ชัน: แสดง "V0.1" ในแอป อ่านจาก `src/lib/version.js` ที่เดียว
- **ทดสอบ:** sales บันทึกการจ่ายบนมือถือ → หน้าจอ owner บนคอมอัปเดตเองภายในไม่กี่วินาที

### V1 รอบ ก — หน้าจอ (ไม่แก้ database) ✓ (11 ต.ค.)

- **เลิกใช้ `input type="date"` / `type="month"` ของเบราว์เซอร์ทั้งแอป** → ทำช่องของแอปเอง
  (`src/components/DateField.jsx`)
  - **ช่องข้อความช่องเดียว พิมพ์เองได้ + ไอคอนปฏิทิน** (แบบ dropdown 3 ช่องทำไปแล้วแต่
    **ลูกค้าปฏิเสธ 11 ต.ค.** → ดู progress.md "V1 รอบ ก" ข้อ 1ก)
  - ลำดับ **วว/ดด/ปปปป** (บัญชีเดือน **ดด/ปปปป**) ทั้งสองภาษา · พิมพ์ได้แต่ตัวเลข แอปใส่ "/" ให้เอง
  - ปี 4 หลัก **>= 2400 ถือเป็น พ.ศ.** ต่ำกว่าเป็น ค.ศ. · ยอมรับ ค.ศ. 1900–2200
  - **ปฏิทินของแอปเอง** (ไม่ใช้ไลบรารี): ชื่อเดือนไทย ปี พ.ศ. หัวคอลัมน์ อา จ อ พ พฤ ศ ส
    ปิดด้วย Esc หรือคลิกนอกกล่อง ใช้บนมือถือได้ไม่ล้นจอ
  - บรรทัดใต้ช่องแสดงวันที่ที่ระบบเข้าใจเป็นคำเต็ม ("ศุกร์ 9 ตุลาคม 2569") หรือข้อความเตือน
  - อังกฤษ: ชื่อเดือนภาษาอังกฤษ ปี ค.ศ. **ลำดับเดิม dd/mm/yyyy**
  - **แปลงเป็น ค.ศ. ก่อนส่ง database เสมอ** (ค่าเข้า-ออกเป็น ISO ค.ศ. · พ.ศ. เป็นแค่การแสดงผล)
  - **ตรวจวันที่ไม่มีจริง** (31 ก.พ.) → ส่งค่าว่าง บันทึกไม่ได้ + ข้อความบอกจำนวนวันของเดือนนั้น
- **ปุ่ม "เพิ่มการจ่าย" บนการ์ดในหน้าตาราง** — เฉพาะ sales และเฉพาะการ์ดที่ยังค้าง
  กดแล้วเปิดฟอร์มการจ่ายเดิมทับหน้าตาราง ไม่ต้องเข้าหน้ารายละเอียด
  และ **การกดปุ่มต้องไม่เปิดหน้ารายละเอียดไปด้วย**
- **ไม่มี migration** · ไม่แตะ RLS, trigger, view · `APP_VERSION` ยังเป็น `V0.1`
- เอกสาร: เติมผลวัด V0.1 ใน `prd.md` ข้อ 12 · เพิ่มกฎใน `AGENTS.md` (ui-reference หยุดที่ V0.1
  ให้ยึด progress.md แทน · ช่องวันที่ต้องใช้ `DateField` / `MonthField` เท่านั้น พร้อมรูปแบบที่ตกลงแล้ว)
- **ทดสอบ:** ดู `progress.md` หัวข้อ "V1 รอบ ก" ข้อ ก–จ (27 ข้อ) — ข้อที่สำคัญที่สุดคือ
  พิมพ์วันที่เป็น พ.ศ. แล้วบันทึก → วันที่ในหน้ารายละเอียดต้องตรง (ไม่เพี้ยนไป 543 ปี)
  **ผ่านแล้ว 11 ต.ค. บนคอม (2 บัญชี)** · ค้าง: ข้อ 23 (เรียก API ตรง) และ ข้อ จ. มือถือ

### V1 รอบ ข — หมายเหตุ + ระบบ feedback (แก้ database) — **เสร็จ 12 ต.ค. 2569** (รัน 005 + ทดสอบ 2 บัญชีผ่าน · เหลือทดสอบบนมือถือหลัง deploy)

> รายละเอียดสิ่งที่ทำ, วิธีรัน `005_notes_and_feedback.sql` และวิธีทดสอบด้วย 2 บัญชี (ข้อ ก–ช)

    → ตารางเป็นประวัติในตัว จึงไม่ต้องเขียน `audit_logs` (ข้อยกเว้นที่ระบุไว้ใน schema.md ข้อ 3.6 + AGENTS.md)
  - ต้องมี migration ใหม่ + RLS ในไฟล์เดียวกัน + อัปเดต `schema.md` ในคอมมิตเดียวกัน

- **ระบบเก็บ feedback** (เงื่อนไขอาจารย์ — prd.md ข้อ 11 **ตกลงจบแล้ว 12 ต.ค.** ทั้ง 3 ข้อ)
  ตาราง `app_feedback` (schema.md ข้อ 3.7) · เมนู "ส่งความคิดเห็น" ในเมนูชื่อผู้ใช้มุมขวาบน

- **ตั้งเป้าหมายในตาราง `prd.md` ข้อ 12 ร่วมกับลูกค้า** — **ตั้งแล้ว 3 แถว (13 ต.ค.)**

  เพิ่มการ์ด/บันทึกการจ่าย = ~30 วินาที) · **ผลวัดของ V1 เติมแล้วทั้งคอลัมน์**

> ตัวเลขวัดผลของ V1 อยู่ใน `prd.md` ข้อ 12 คอลัมน์ **V1**

### 1. สรุปตารางรายเดือน + ส่งออก PDF / JPG (คำขอของเจ้าของ 13 ต.ค.)

- **ที่มา:** เจ้าของขอ **"สรุปตารางรายเดือน ส่งออก PDF / JPG พิมพ์ได้"**
  (ผลสัปดาห์แรก ข้อ 8) · ตรงกับงาน "ส่งออก JPG / PDF" ที่ M7 วางไว้
- **ทำไมสำคัญ:** สัปดาห์แรกลูกค้ายังใช้แอป **คู่กับ** ตารางกระดาษ งานนี้คือสิ่งที่ทำให้
  **เลิกตารางกระดาษได้จริง** → กระทบแถว "เวลาที่ฝ่ายขายใช้ทำตารางสรุปต่อเดือน"
  ของ `prd.md` ข้อ 12 ที่ต้องวัดซ้ำตอนสิ้นเดือน
- **ยังต้องตกลงกับลูกค้าก่อนเขียนโค้ด** (ห้ามเดา — AGENTS.md):
  - ตารางรายเดือนแสดงคอลัมน์อะไร เรียงอย่างไร และรวมยอดแบบไหน
  - นับตามเดือนบัญชี (`account_month`) หรือเดือนที่เงินเข้า
  - การ์ดที่ยกเลิกและการ์ดที่ค้างข้ามเดือนแสดงหรือไม่
  - PDF / JPG อย่างละ 1 หรือทั้งคู่ · ขนาดกระดาษ (A4) และแนวตั้ง/แนวนอน
  - ใครส่งออกได้ (เจ้าของเท่านั้น หรือฝ่ายขายด้วย) → ต้องอัปเดตตารางสิทธิ์ prd.md ข้อ 9
- **ข้อจำกัดที่ต้องเคารพ:** ยอดและวันทั้งหมดอ่านจาก `receivable_summary`
  (ห้ามคำนวณใหม่ใน JavaScript — AGENTS.md) · วันที่ในไฟล์ที่ส่งออกใช้รูปแบบไทย วว/ดด/ปปปป พ.ศ.
  เหมือน `DateField` · **ไม่มีข้อมูลลูกค้าจริงหลุดลง repo** (ไฟล์ตัวอย่างต้องใช้บริษัท `[TEST]`)
- **ทดสอบ:** เปิดไฟล์ที่ส่งออกบนมือถือและพิมพ์จริง 1 แผ่น · ยอดในไฟล์ตรงกับหน้าจอ ·
  ทดสอบด้วย 2 บัญชี (ถ้าตกลงว่าฝ่ายขายส่งออกไม่ได้ ต้องถูกบล็อกจริง ไม่ใช่แค่ซ่อนปุ่ม)

### 2. ปิดคำถามที่ค้างกับลูกค้า (ทำก่อนหรือพร้อมข้อ 1)

- **เป้า "ความสดของข้อมูล" คือ 1 วันตามปฏิทิน หรือวันทำงานถัดไป** (ผลสัปดาห์แรก ข้อ 7)
  → **ห้ามแก้วิธีนับใน `feedback_report.sql` ก่อนได้คำตอบ**
- **ตั้งเป้า 2 แถวที่เหลือใน `prd.md` ข้อ 12:** "เวลาที่เจ้าของใช้หายอดคงเหลือของบริษัทหนึ่ง"
  และ "ยอดในแอปตรงกับยอดที่ลูกค้าเชื่อถือ"
- **วันครบกำหนดผิด 1 การ์ด (13 ต.ค.) สาเหตุยังไม่ทราบ** → ถ้าเจอซ้ำให้ไล่ `audit_logs`
  ของการ์ดนั้นก่อนแก้โค้ด · ยังไม่มีหลักฐานว่าแอปคำนวณผิด **จึงยังไม่แก้อะไร**
- **ขอคำตอบ feedback ข้อ 4 ซ้ำตอนสิ้นเดือน** แล้วเติมแถว "ตารางสรุปต่อเดือน" ของ V1 ให้เป็นค่าจริง
